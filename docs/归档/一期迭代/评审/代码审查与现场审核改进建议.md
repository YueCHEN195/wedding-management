## 总体判断

现有代码是功能覆盖较完整的演示版本，前后端结构清晰，路由按功能拆分，密码有哈希，金额设计采用分，后台接口有身份与部分角色检查，请柬与后台有页面懒加载。约 150 人的单场婚礼，Hono + SQLite + React 完全可以继续使用。

主要欠缺是业务一致性、身份匹配、可恢复性和现场操作设计。优先解决错人、重复签到、重复礼金和半成功写入，再做界面。无需为这些问题更换 CloudBase、增加 Redis、消息队列或多租户体系。

优先级含义：P1＝正式使用前应修复；P2＝影响准确性、体验或维护，下一轮处理；P3＝可选增强。下文“已复现”指对现有路由实际执行，“代码确认”指静态检查，“设计补充”指现有能力不足，不等于实现违背旧需求。

## 一、业务与数据缺陷

### 1. P1：重名自动关联第一条宾客，而不是交给工作人员选择【已复现】

位置：server/lib/guest.ts:15；server/routes/checkin.ts:23；web/src/admin/ReviewPage.tsx。

数据库有两位同名宾客时，自助提交直接指向第一个 guestId。第二位提交还可能被第一位的待审记录挡住。审核页面没有候选宾客选择控件，确认接口也没有提供更正关联的入参。这既不符合新设计稿，也违背项目内旧 PRD 第 7 条“命中多条由工作人员选择”。

建议：自助提交保留提交姓名与来源；同名只返回受权审核端的候选列表，未核对前 guestId 留空。审核端显示归属方、分组、回执人数等区别，由工作人员明确选择。不要仅凭名字证明身份。无匹配可建临时档案，但要标记来源与待匹配状态。

### 2. P1：通用回执仅凭姓名就能覆盖专属回执【已复现】

位置：server/routes/invite.ts:70–80。

通用接口以姓名唯一匹配到名单后，直接更新该宾客的现有回执。测试中先通过 token 提交“出席 3 人”，再通过通用入口输入相同姓名并选择“不出席”，原回执被修改，整个过程无需私有凭证。

建议：通用提交首次创建独立邀请组/待匹配回执，并返回自己的修改凭证；后续修改必须持有凭证。已有宾客的回执只能通过专属凭证或受权后台修改。人工匹配与合并单独进行。

### 3. P1：同一已确认宾客重新扫码可新增签到与礼金【已复现】

位置：server/routes/checkin.ts:24–43；server/routes/checkins.ts:55–83。

仅检查同一 guestId 的 pending 记录。确认之后再提交同名，返回新的 id、duplicate=false。手动补录每次也直接新增 confirmed 记录。再次审核可重复增加签到记录与礼金。

建议：区分“签到提交”和“当前到场记录”；每邀请组只有一条当前签到，重复到场提交返回已有状态。实际人数修改更新原记录并留日志。幂等 key 用于识别同一次操作的网络重试，不能用“姓名+金额”去重，因为同人真送两笔是合法场景。

### 4. P1：签到与礼金没有事务，失败时留下半成功状态【故障注入复现】

位置：server/routes/checkins.ts:105–112；同样检查手动补录、宾客删除、回执提交。

确认接口先改签到，再插礼金。独立测试数据库通过触发器模拟礼金写入失败，接口返回 500，但签到已是 confirmed，礼金为 0 条。重试又被“已确认”挡住，工作人员可能误认为礼金已登记。

建议：相关写入置于同一事务，包括签到、礼金、关联、日志、幂等结果；任何一步失败整体回滚。宾客删除和回执状态更新也需要事务。异步参数解析先完成，再进入同步数据库事务。

### 5. P1：并发确认存在检查与写入间隙，可登记两笔礼金【受控时序复现】

位置：server/routes/checkins.ts:88–112。

接口读取 pending 状态后，等待请求体解析，再无条件更新。普通同时请求在本次测试中返回 200/409；人为延迟其中一个请求体后，另一请求先完成确认，延迟请求仍依据旧状态写入，最终两次 200、同一 checkinId 两条礼金。

建议：事务内重新验证状态，用 `UPDATE ... WHERE id=? AND status='pending'` 检查受影响行数，只有成功改变状态的请求可创建礼金。审核生成的礼金关联应有适当唯一约束，独立礼金可多笔；编辑增加 version，冲突提示“已由其他操作更新，请刷新后确认”。

### 6. P1：工作人员可以删除已确认签到并连带删除礼金【已复现】

位置：server/routes/checkins.ts:117–127。

DELETE 路由只要求登录，没有限制只能驳回 pending。staff 调用后，confirmed 签到和关联礼金都被物理删除，绕过了 gifts DELETE 仅管理员的限制。

建议：驳回入口仅处理待审记录；撤销确认、作废礼金是独立操作并按角色检查。撤销签到不要自动销毁礼金。即使保留旧 PRD 的“驳回即删除”，也至少不能删除已确认记录与账目。

### 7. P1：后端缺少有效的运行时校验，异常值实际能进入数据库【已复现】

位置：server/routes/invite.ts、rsvps.ts、gifts.ts、checkins.ts；server/db/schema.ts。

`as Attending` / `as GiftMethod` 只是类型断言，不校验请求。Drizzle 的 text enum 在现有迁移中没有生成 CHECK。测试提交 attending=invalid、headcount=1.5、childrenCount=99，返回 200 并保存。礼金只检查有限且非负，没有要求安全整数、金额上限或合法方式；确认 amount=null/空串会被 Number 转为 0，绕过“必填”。非法枚举也会使图表分类和统计行为异常。

建议：利用已安装的 Zod 建统一请求 schema；人数为整数、总人数 1–20（后台可处理超限）、儿童不大于总人数；不出席为 0，待定不计已确认；金额为非负安全整数分、业务上限可配置，正式礼金记录建议正数，0 作为“本次未记礼金”选项而非零元账目；姓名、备注、留言限制长度；ID 必须正整数且关联存在。数据库补 CHECK、必要外键与唯一约束。

### 8. P2：通用回执“更新”会新增并重复统计【已复现】

位置：server/routes/invite.ts:20–53、70–80；web/src/invite/InvitePage.tsx:98–109。

名单外宾客 guestId=null，每次保存新行。测试同名提交两次返回不同 id、数据库两条记录。前端却显示“更新回执”“已收到，可再次修改”。出席人数会累加，刷新后也没有自己的回执恢复入口。

建议：首次创建自己的记录与凭证，之后更新同一记录。数据库对非空 guestId 的当前回执建立唯一约束，历史修改单独留日志。历史重复数据应先人工核对，不能直接按姓名合并。

### 9. P2：“实际签到人数”其实是签到记录条数，缺少实际人数模型【代码确认／设计补充】

整改进度（2026-10-15）：已实现实际总人数与儿童登记、组数独立统计、旧签到补记、更正人数审计与导出，用户验收通过。[复现与验收说明](../问题整改/09-实际到场人数与签到组数/README.md)。以下保留原始发现。

位置：server/db/schema.ts:49–62；server/routes/stats.ts:21；web/src/admin/DashboardPage.tsx。

回执支持一组多人的预计人数，但签到没有 actualTotal。一家三人只签代表姓名时统计为 1；重复记录又会增加“人数”。这是新设计稿与旧实现模型的关键差别。

建议：保留宾客扫码只填姓名的简单体验，由工作人员在审核端核对实际人数。分别显示“预计出席 X 人”“已到场 Y 人”“已签到 Z 组”；儿童是总人数子集。签到不自动覆写回执。

### 10. P2：标记已发送会把已查看／已回执退回 sent，污染统计【已复现】

位置：server/routes/guests.ts:121–130；server/routes/stats.ts:18–20。

对已回执宾客点击“标记已发送”，status 无条件变 sent；rsvp 仍存在，但 dashboard 的 rsvpCount 只计算 status='rsvp'，变少。现场新建的散客也会进入 guestTotal，却不代表已邀请组数。

建议：邀请发送、首次查看、回执意向、签到状态拆开表达，不用一个互斥 status 承载全部。近期可先禁止状态降级，回执统计从实际回执记录计算。

### 11. P2：确认时输入的备注在签到记录里丢失；金额为 0 时完全丢失【代码确认】

位置：server/routes/checkins.ts:100–112。

确认接收 note，只存 gifts；更新 checkins 没有 note。金额为 0 不建 gifts，备注没有任何保存位置。签到列表读的是 checkins.note，工作人员写了备注却看不到。

建议：签到备注和礼金备注明确分开，或者明确共享字段并同步保存；没有礼金也应保留现场备注。表单打开时显式清空上一位的所有字段，不能只 setFieldsValue 金额与方式。

## 二、礼金账本与权限补充

### 12. P1/P2：礼金缺少待核对、到账确认、作废、修改日志【设计补充】

整改进度（2026-10-15）：已补新增和更正日志、前后值及原因、版本保护和冲突核对；作废恢复也递增版本。[本项验收记录](../问题整改/12-礼金更正留痕与并发保护/README.md)。待核对、到账确认及收款人等流程尚未实施，以下保留初次审查内容。

现有 gifts 只有金额、方式、时间和关联，不记录操作者、收款人、红包编号、version、状态；统计汇总所有记录；编辑直接覆盖，删除物理销毁。旧需求接受这种简化，新稿要求可追溯账本，两者需明确选择。

建议最小补充：PENDING / CONFIRMED / VOIDED；只有已核对且未作废金额计入已收总额。确认后改金额或方式回到待核对。新增 append-only 操作日志（操作者、对象、动作、前后值、时间），作废填原因。一位工作人员也需要日志，主要用于误操作恢复和事后查账。

### 13. P2：合送、多收款方式与未到场送礼表达不足【设计补充】

现有独立新增礼金允许 guestId=null，已经能录未到场礼金，这是可保留的基础。但一个 gifts 只能关联一个 guestId；人工新增前端只写姓名、不选择已有宾客，因此个人详情可能漏掉这笔。

建议：礼金署名单独字段；gift_guest_links 支持关联多个邀请组且金额只汇总一次。现金+微信混合送礼记两笔。允许不关联签到录礼金；查人和登记礼金不要求先到场。近期先增加宾客选择、独立礼金入口即可，多对多可后补。

### 14. P2：staff 只读搜索仍收到整条宾客凭证，界面与权限不一致【已复现／代码确认】

位置：server/lib/dto.ts:10–27；server/routes/guests.ts:16–62；web/src/admin/GuestsPage.tsx:96、125。

staff 的宾客列表包含 phone、note、inviteToken、inviteUrl；列表姓名点击详情返回 403，标记已发送按钮也会返回 403，而且该操作没有 onError。普通查看权限不应默认授予可修改回执的凭证。

建议：角色对应受限 DTO；现场搜索返回辨认所需的姓名、分组、归属、回执与签到信息，不返回 inviteToken。staff 详情提供受限版本，发送、海报等管理员按钮按权限隐藏。若继续允许 staff 查看全部单笔礼金，就只能保证“不显示总额”，不能保证无法自行汇总；新稿中签到员不看金额属于新增权限设计，不能当成旧实现违约。

### 15. P2：登录保护与会话撤销不足【代码确认】

位置：server/routes/auth.ts:13；server/auth/middleware.ts:14–23；server/env.ts。

登录接口没有限频；生产环境未强制拒绝默认或空 JWT_SECRET；JWT 内角色有效一周，逐请求不核对账号是否仍存在/已停用，因此账号撤销或改角色不会立即失效。密码哈希与 HttpOnly Cookie 已具备。

建议：生产启动检查密钥与初始密码配置；按账号+可信客户端来源限制连续失败；鉴权核对账号状态/sessionVersion。普通使用可以保留两个角色，不急于开发复杂成员管理。

### 16. P2：专属请柬分享携带可修改凭证【代码确认】

位置：web/src/invite/InvitePage.tsx:117–129；server/index.ts:37；server/lib/dto.ts。

“分享请柬”直接分享 window.location.href，专属路径包含 token；接收者能修改原宾客回执。Hono logger 也会记录含 token 的请求路径。当前 token 随机性足够，但没有过期、撤销或重发能力。

建议：分享动作始终生成通用 /invite 链接；提醒专属凭证仅用于本人回执；支持重置 token；日志掩码。凭证摘要存储和 fragment 携带可后续增强，注意相应改造海报、二维码、接口与缓存策略。

## 三、界面与防误操作

### 17. P1：0 元被默认填入，无法区分“未核对”和“确实没有礼金”【代码确认】

位置：web/src/admin/ReviewPage.tsx:99；server/routes/checkins.ts:95–99。

打开确认弹窗，金额预填 0，方式预填微信。工作人员可以未核实任何信息直接点击“确定”，系统把未知当成无礼金。

建议：签到确认是主操作；礼金区用“暂不登记 / 已收礼金”明确选择，默认不把金额推断为 0。已收礼金必填金额与方式，显示格式化预览。较大金额才做针对性二次核对，不要每条弹两个确认框。保存失败保留输入并显示尚未保存。

### 18. P1/P2：查询失败与空列表混淆，可能造成现场虚假安心【代码确认】

位置：web/src/admin/ReviewPage.tsx:64–88；各列表与 DashboardPage。

pending.data ?? [] 把初次请求失败、加载中与真的无待审记录一起显示“暂无待审核提交”。已有数据刷新失败时也没有更新时间与断网提示。仪表盘统计失败部分位置以 0 展示，容易误读。确认/新增有错误提示，但驳回、删除、发送等多处缺少 onError。

建议：四种状态分开：加载、成功且为空、失败、保留旧数据但更新失败；显示“最近更新 HH:mm:ss”“连接失败，当前显示旧数据”，支持重试。轮询保留选中项与表单，金额输入时不要跳到新插入记录。待审按提交先后顺序处理，当前 desc 会让新记录插到最前。

### 19. P2：跨页面缓存更新不全、切换账号未清缓存【代码确认，未浏览器复现】

ReviewPage 保存只 invalidate checkins/stats，不刷新 gifts、guests、guest-detail；GiftsPage 不刷新 checkins/detail；RsvpsPage 不刷新 guests/stats。默认不在焦点恢复时刷新，使用户切页后可能短暂或持续看到旧汇总。

退出只 invalidateQueries，登录只刷新 me；QueryClient 缓存不是按账号隔离。应明确移除敏感业务缓存并取消旧请求，避免管理员礼金汇总留在 staff 会话内存中。

建议：集中定义每个业务动作影响的查询键；登录/退出清空敏感缓存或按用户隔离查询键；401 给出明确登录过期提示，并提供保留非敏感输入的可恢复路径。

### 20. P2：通用“确定”、小文字链接、嵌套卡片增加判断负担【设计建议】

现场确认按钮改成“确认到场”或“确认到场并登记 ¥600.00”；驳回改“标记无效”，低优先级放更多菜单，并保留原因与恢复入口。显示姓名、匹配对象、预计/实际人数；时间与来源作为辅助信息。

视觉建议：后台用白/浅灰平面背景、细分隔线、小圆角（4–6px）、单一主色与足够留白；减少阴影、渐变、重复 Card、过多彩色 Tag。正文 14–16px，现场姓名更大；核心操作用有文字的按钮，触控区至少约 44px。金额带元单位、两位小数、千分位；危险操作与主操作留距离。保留 Ant Design，先统一主题和页面结构。

手机现场端更简洁：姓名→提交→明确待确认结果，人数可以由工作人员补充；避免“再签一位”暗示同一组每人都必须重复登记。请柬保留婚礼情绪，但用更克制的平面排版、直接展示核心时间地点与回执入口。

### 21. P2/P3：请柬容错、地图、动效和可访问性仍需补足【代码确认】

InvitePage 初始加载只处理 404，其余错误被吞掉，之后仍显示普通页面；切换 token 时未完整重置上一个宾客状态。打开请柬后仍保留一整屏封面，缺少自动定位/直接回执入口。使用 alert 报错，没有贴近字段的错误说明；标签缺少关联输入、出席按钮缺少选中语义；图片没有懒加载/尺寸占位/失败备用内容，动效没有减少运动设置。

地图按 UA 跳系统链接，没有复制地址降级；微信中能否唤起需真机检查。倒计时婚期过后一直显示“今天，我们结婚啦”，应区分当天与婚后。手机号、地点、婚期与素材仍是 demo，需要上线前核对。

## 四、工程与部署

### 22. P1：备份说明在 WAL 模式下不安全【代码与文档确认】

位置：server/db/client.ts 的 WAL 设置；[技术设计的备份章节](../../../技术/技术设计.md)。

文档说定期复制 wedding.db 即可；运行中最新事务可能在 wedding.db-wal，单独复制主文件可能丢失最新数据。只导出 Excel 也不能恢复账号、凭证与所有关联。

建议：实现 SQLite 在线备份或 sqlite3 .backup 的一致性快照，婚礼前实际恢复演练，核对宾客、回执、签到、礼金笔数/金额/关联。异地副本与备份保留规则要明确。长期保存数据需要恢复能力。

### 23. P2：生产首次部署只迁移不创建账号【代码确认】

Docker 启动 pnpm start，server/index.ts 只 runMigrations，不 seed。README 的 Docker 部署流程没有独立初始化账号步骤。全新 data 目录会有表但没有可登录账号，和本次 admin 登录问题是同类缺口。

建议：提供只初始化后台账号的显式命令，生产不要自动写 demo 宾客；只在账号不存在时创建，修改环境变量不等于重置已有密码。README 增加初始化与安全重置步骤。Docker 未实际构建，原生模块 allowBuilds 在安装阶段的可用性还需验证。

### 24. P2/P3：列表与统计全表扫描，图表依赖偏重【代码确认／构建验证】

gifts/checkins/rsvps 拉全表后在 JS 中切页，签到列表每次还扫描所有 gifts，pending 没有上限。当前 150 人规模性能问题不突出，但永久保存数据后会放大。缺少 guestId、checkinId、status/time 查询索引；开启 foreign_keys pragma 并不能弥补 schema 没有外键。

建议：数据库完成 count/limit/offset/sum，签到关联查询仅查询本页 IDs；补针对实际查询的索引。先修正确性，不做大规模性能架构。

生产构建成功，但 DashboardPage 块约 1,137.63KB（gzip 378.11KB），主要图表依赖值得按需裁剪或用简单柱条替代；这主要影响后台首页，不能误称整个请柬首屏都下载此块。现有按页面懒加载值得保留。

### 25. P2/P3：导入验收与工程护栏不足【代码确认】

前端允许 .xls，但后端仅 wb.xlsx.load；复杂单元格直接 String(cell.value) 可能变成 [object Object]；失败明细仅提示数量，无导入预览、标准模板和重复导入处理，文件大小/行数无上限。没有测试脚本或现成业务回归套件。pnpm/npm 两份锁文件并存；没有固定 packageManager 与 .nvmrc，容易重现 Node 环境不一致。Zod 已安装但业务接口未使用。

建议：先明确只支持 .xlsx，显示成功与失败逐行结果，提供模板与预览；去重由人工确认，不强行按姓名。固定 Node24/pnpm 版本，保留统一锁文件策略。新增针对状态、金额、幂等、权限、故障回滚的回归测试，避免只写类型或渲染快照测试。

## 五、现场审核的建议流程

实施进度（2026-10-15）：现场工作台已改为队列与审核工作区，支持按先后处理、状态区分、未保存保护、保存结果预览及窄屏布局，用户验收通过。[本次复现与验收记录](../问题整改/现场审核工作台与平面化界面/README.md)。原有默认登记礼金、默认现金按用户已验收设置保留；其他页面的状态容错和视觉统一尚未在本项全部处理。

采用“现场工作台”，把待审核、查人/代签、已处理记录放在一个工作区内。保留工作人员单笔礼金权限的当前边界；如果未来签到与记账由两个人分工，再拆权限，不强迫现在增加成员体系。

桌面建议左侧待审队列、右侧固定审核详情；手机转单列。待审队列按先到先处理，姓名、等待时间、同名/新增/重复提示。选中后核对：提交姓名→匹配邀请组→实际人数→可选礼金→保存结果。异常记录进入待核对区，不强迫工作人员当场猜测。

默认只需确认到场；已收礼金时展开金额、收款方式、红包编号/备注，按钮文字明确包含结果。未知金额用“待核对”，和“没有随礼”分开。工作人员输入中的表单不受轮询替换影响；关闭未保存表单时提示；已被别人处理时保留输入并显示最新状态，不静默覆盖。

同名选择候选必须明确；已经确认的邀请组提供“查看/更正人数”，不再次新增；重复提交标记并返回同一处理结果。无名单宾客能接待、能建临时组，后续由管理员合并。合并在事务内，保留来源与历史，不能按名字自动合并。

保存成功后展示姓名、实际人数、礼金是否登记以及金额，才切到下一条。弱网超时显示“结果待确认”，凭同一幂等 key 查询/重试，禁止新建另一笔。确认到场撤销与礼金作废分开。

## 七、实施顺序与验收

第一批：匹配、回执凭证、请求校验、事务、幂等、条件更新、删除权限、统计口径；这些决定是否能正式使用。

第二批：现场工作台、统一主题、清晰状态/错误、空金额与待核对区分、缓存一致性、手机布局。不要只改色与圆角后宣称防呆完成。

第三批：礼金状态/日志/作废、合送关联、初始化与重置脚本、备份恢复、导入预览、图表裁剪。若婚礼临近，备份和账号演练提前到第一批。

核心验收：两位同名不串档；一家三人到场统计3人1组；重复扫码不增人数；一次操作超时重试只记一笔；两端确认只有一个成功；礼金写失败整笔回滚；staff不能删除已确认礼金；未知金额不被当成0；已确认金额修改重新核对；无凭证不能覆盖他人回执；通用修改不新增；失联显示旧数据与时间；备份在隔离环境恢复金额和关联一致。
