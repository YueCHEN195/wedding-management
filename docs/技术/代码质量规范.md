# 代码质量与分层规范

## 目的与边界

提高代码的可读性、修改安全性和复用效率。ESLint检查可靠性与依赖边界，Prettier处理缩进、换行和格式；TypeScript负责类型检查，业务测试负责行为。任何一项都不能替代其他检查。

参考[ESLint Flat Config](https://eslint.org/docs/latest/use/configure/configuration-files)、[typescript-eslint推荐配置](https://typescript-eslint.io/users/configs/)、[React官方Hooks规则](https://react.dev/reference/eslint-plugin-react-hooks)和[Airbnb模块与函数组织建议](https://github.com/airbnb/javascript)。采用其清晰职责、显式依赖和一致约定的原则，不整体照搬某公司的历史配置，不引入额外状态管理框架或通用CRUD引擎。

## 安装与命令

要求Node >=24，首次安装：

```sh
pnpm install
pnpm lint:setup
pnpm check
```

- `pnpm lint`：扫描server、shared、web、tests、脚本和配置；error阻止通过，历史warning继续显示。
- `pnpm lint:pilot`：当前宾客管理入口与guests功能目录必须零error、零warning。
- `pnpm lint:test`：用代码样例验证视图请求边界、前后端边界、条件Hooks和未处理Promise确实会报错。
- `pnpm lint:fix`：全项目自动修复入口，使用前检查diff；日常优先直接给ESLint指定文件，避免无关变动。
- `pnpm format <文件或目录>`、`pnpm format:check <文件或目录>`：仅操作指定范围，不默认格式化整个仓库。
- `pnpm check`：串行执行lint、试点严格检查、规则测试、应用类型检查、业务测试和生产构建。

项目TS7.0.2仍由根依赖负责。当前typescript-eslint8.71.2官方peer范围为TypeScript >=4.8.4 <6.1，因此按确认方案在tooling/eslint使用独立的TypeScript6.0.3。工具目录有自己的package.json和冻结锁文件，根目录eslint.config.mjs只导出工具配置。没有关闭版本警告、强制安装不兼容peer，也没有降级应用编译器。

ESLint的类型分析使用TS6；应用类型正确性仍以根目录TS7的typecheck为准。以后引入TS7特有语法时，需要先复核lint工具兼容性；上游支持后再统一版本。工具依赖不参与应用构建，嵌套node_modules不进入Docker构建上下文。

## 项目级规则

| 范围 | 强制检查 | 渐进检查 |
| --- | --- | --- |
| TS/JS基础 | 推荐错误规则、未用变量、重复导入、const/let、相等比较 | 类型导入、显式any |
| React | Hooks调用顺序 | effect依赖、编译器相关诊断、未处理/误用Promise |
| 层级 | 前端不得导入server；server不得导入web；shared不得依赖页面或UI框架 | 复杂模块逐步迁移 |
| 已声明纯视图 | 禁止运行时导入API客户端、React Query、server；允许DTO类型导入 | 依赖间接绕行仍需代码评审 |
| 宾客试点 | any、未处理Promise、effect依赖升级为error，整体不允许warning | 每个新迁移模块扩大该范围 |

长度提醒：文件350行、函数200行、复杂度20、嵌套4层。测试文件豁免长度限制，但保留正确性检查。阈值是项目选择，不是“大厂标准”；纯声明、配置和JSX长度应结合职责判断。不能以压行、拆成无意义的小函数或eslint-disable绕过检查。

已有历史代码不批量ignore，也不通过suppressions隐藏。迁移时处理相关警告后加入严格范围。合理例外需要精准到规则/范围并写明原因；eslint会检查无效disable。

## 视图与逻辑如何拆分

- **页面组合**：角色入口、区块顺序、工具区、展示反馈；简单页面无需额外Hook。
- **功能Hook**：查询参数、query/mutation、缓存刷新、提交状态、并发响应保护、未保存保护；复用现有API客户端和React Query。
- **功能视图**：表格列、表单字段、抽屉Header/Body/Footer、详情排版；通过props获取数据与操作。AntD Form、焦点与本地展示状态可以留在视图。
- **共享组件**：只有跨功能稳定重复的模式才提取；不把业务名称、权限或金额规则塞进通用组件。
- **业务计算**：继续使用shared和server已有能力，不在Hook中重写服务端状态、人数或金额规则。

新纯视图命名为`*.view.tsx`；当前宾客功能中的Guest*.tsx也已纳入强制边界。现有其他页面不是通过改名就自动完成迁移；请求、状态与副作用都应实际移出视图。

宾客管理示范：

| 文件 | 责任 |
| --- | --- |
| GuestsPage.tsx | 角色路由、页面区块、导入结果和媒体展示 |
| guests/useGuestManagement.ts | 查询、编辑生命周期、保存、导入、缓存与离开保护 |
| guests/GuestListTable.tsx | 列定义、单行密度、分页展示 |
| guests/GuestEditorDrawer.tsx | 固定页脚、表单及原有校验呈现 |
| guests/GuestDetails.tsx | 只读档案、回执、签到及礼金记录 |
| guests/guestMenu.tsx | 同一业务菜单在列表和详情间复用 |
| guests/guestFeedback.tsx | 复制链接回退与部分导入反馈 |

组件用Pick限定收到的模型字段，避免手写一套重复状态类型；模型类型由Hook返回值推导。该模型仅服务宾客功能，不是项目级Controller框架。
