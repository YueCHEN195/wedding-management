## 1. 设计目标与约束

| 目标 | 说明 |
| --- | --- |
| 极简运维 | 一个服务、一个数据库文件、一条命令部署，新人自己能维护 |
| 低依赖 | 依赖越少越好，避免引入不需要的中间件（Redis / MQ / 对象存储等） |
| 稳健 | 婚礼当天必须可用；数据不丢 |
| 好看 | 请柬页要有质感，动效流畅；后台要高效 |
| 规模 | 宾客约 150 人，峰值并发很低，单机绰绰有余 |

约束（来自需求）：
- 自建服务器 + Docker 部署
- 婚礼信息写死在代码中，无配置后台
- 两个账号（管理员 / 工作人员），权限不同
- 三个前端界面：PC 后台、手机请柬页、手机自助签到页

## 2. 技术选型（推荐）

### 2.1 总览

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 语言 | **TypeScript**（前后端统一） | 类型共享、维护简单 |
| 运行时 | **Node.js 24 LTS**（Docker 镜像；本地同为 Node 24） | 稳定、生态好 |
| 包管理 | **pnpm**（单一工程） | 快、省磁盘 |
| 前端框架 | **React 19 + Vite 8** | 生态成熟、构建快 |
| 前端路由 | **React Router v7** | 三端按路由分组 |
| PC 后台 UI | **Ant Design 6** | 表格 / 表单 / 弹窗开箱即用，后台开发最快 |
| 手机端样式 | **Tailwind CSS** | 自定义国风样式灵活 |
| 手机端动效 | **framer-motion**（或纯 CSS） | 请柬入场动画 |
| 图表 | **ECharts**（echarts-for-react） | 后台看板 |
| 后端框架 | **Hono** | 轻量、TS 优先、API 简洁、内置 JWT/Cookie/静态资源 |
| 数据库 | **SQLite**（better-sqlite3，WAL 模式） | 单文件、零运维、快 |
| ORM / 迁移 | **Drizzle ORM + Drizzle Kit** | 类型安全、迁移清晰、贴近 SQL |
| 参数校验 | **zod** | 接口出入参校验 |
| 密码 | **bcrypt** | 哈希存储 |
| 会话 | **JWT（jose / Hono jwt）+ httpOnly Cookie** | 无状态、简单 |
| 二维码 | **qrcode** | 生成 PNG/SVG |
| 海报合成 | **sharp** | 把二维码贴到底图上，快且稳 |
| 批量打包 | **archiver** | 海报 / 导出的 ZIP |
| Excel | **exceljs** | 导入导出，可带表头样式 |
| 反向代理 / HTTPS | **Caddy** | 自动申请续期证书，配置极简 |
| 容器 | **Docker + docker-compose** | 一键起 |

### 2.2 为什么这样选

- **一台服务搞定所有**：Hono 同时提供 API 与静态资源（SPA 回退），生产环境只有一个 Node 进程 + 一个 Caddy。
- **SQLite 足够**：150 人、低并发，SQLite（WAL）性能完全够，还省掉数据库运维和网络往返。数据就是一个文件，备份=复制文件。
- **Drizzle 而非 Prisma**：更轻、更贴近 SQL、运行时不引入额外引擎。
- **后台用 Ant Design**：后台的核心是表格与表单，Ant Design 直接省掉大量组件开发。
- **手机端用 Tailwind**：请柬要精细定制，组件库反而碍事。

### 4.2 关系

```
guests 1 ──< rsvps        (guest_id, 可空)
guests 1 ──< checkins     (guest_id, 可空)
guests 1 ──< gifts        (guest_id, 可空)
checkins 1 ──< gifts      (checkin_id, 可空)
```

### 4.3 状态与枚举汇总

| 枚举 | 取值 |
| --- | --- |
| 宾客状态 `guest.status` | `pending` 待邀请 / `sent` 已发送 / `viewed` 已查看 / `rsvp` 已回执 |
| 签到状态 `checkin.status` | `pending` 待审 / `confirmed` 已确认 |
| 签到来源 `checkin.source` | `self` 自助 / `manual` 补录 |
| 回执 `rsvp.attending` | `yes` / `no` / `maybe` |
| 礼金方式 `gift.method` | `wechat` / `alipay` / `cash` |
| 账号角色 `user.role` | `admin` / `staff` |

## 5. 接口设计

统一前缀 `/api`。鉴权用 httpOnly Cookie 中的 JWT；接口按角色做中间件校验。

### 5.1 鉴权

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/auth/login` | 公开 | 账号 + 密码登录，下发 Cookie |
| POST | `/api/auth/logout` | 登录 | 退出 |
| GET | `/api/auth/me` | 登录 | 当前用户与角色 |

### 5.2 后台 · 宾客（staff 只读搜索，其余 admin）

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/guests` | admin/staff | 列表、筛选、分页（staff 只读） |
| POST | `/api/guests` | admin | 新增 |
| PATCH | `/api/guests/:id` | admin | 修改 |
| DELETE | `/api/guests/:id` | admin | 旧物理删除已关闭（409），改用归档／恢复 |
| POST | `/api/guests/import` | admin | Excel 导入 |
| GET | `/api/guests/export` | admin | 导出 Excel |
| GET | `/api/guests/:id/qr` | admin | 返回该宾客二维码图片 |
| GET | `/api/guests/:id/poster` | admin | 返回该宾客海报图片 |
| GET | `/api/guests/:id/detail` | admin | 单个宾客的回执 / 签到 / 礼金汇总 |
| GET | `/api/posters/export` | admin | 批量海报 ZIP |

### 5.3 后台 · 回执 / 签到 / 礼金 / 统计

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/rsvps` | admin | 回执列表与统计 |
| PATCH | `/api/rsvps/:id` | admin | 代填 / 修改 |
| GET | `/api/checkins` | admin/staff | 签到列表（可按 `status=pending` 轮询） |
| POST | `/api/checkins` | admin/staff | 手动补录签到 |
| PATCH | `/api/checkins/:id/confirm` | admin/staff | 审核确认（同时写入礼金） |
| DELETE | `/api/checkins/:id` | admin/staff | 旧物理删除已关闭（409），改用带原因的状态操作 |
| GET | `/api/checkin/qr` | admin/staff | 现场入口总码图片（编码 `/checkin` 链接） |
| GET | `/api/gifts` | admin/staff | 礼金流水（**staff 只返回单笔，不返回汇总**） |
| POST | `/api/gifts` | admin | 新增礼金 |
| PATCH | `/api/gifts/:id` | admin | 修改 |
| DELETE | `/api/gifts/:id` | admin | 旧物理删除已关闭（409），改用作废／恢复 |
| GET | `/api/stats/summary` | admin | 看板关键指标 |
| GET | `/api/stats/charts` | admin | 图表数据 |
| GET | `/api/export/:type` | admin | 导出（guests/rsvps/checkins/gifts） |

### 5.4 公开接口（宾客）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/invite/:token` | 专属请柬数据（含宾客信息与已有回执）；顺带把状态推进为 `viewed` |
| POST | `/api/invite/:token/rsvp` | 提交 / 覆盖回执 |
| GET | `/api/invite` | 通用请柬数据（不含宾客） |
| POST | `/api/invite/rsvp` | 通用链接提交回执（需填写姓名） |
| POST | `/api/checkin/self` | 自助签到：提交姓名 → 生成 `pending` 记录 |

公开接口加基本限流（按 IP），token 使用足够长的随机串（≥ 22 位 Base62）。

### 5.5 关键流程（审核确认）

```
POST /api/checkins/:id/confirm
  body: { amount: number(分, 必填, 可为0), method: 'wechat'|'alipay'|'cash', note?: string }
  →
    1. checkin.status = confirmed，记录 confirmed_at
    2. 若 amount > 0 → 插入一条 gift（checkin_id 关联）
    3. 若 amount = 0 → 不生成礼金记录
  事务内完成。
```

- **驳回／撤销**：通过统一状态操作接口保留原记录；已确认签到仅管理员可撤销，礼金不随之删除或作废。旧DELETE接口返回409。
- **只随礼未签到**：`POST /api/gifts`（不传 checkin_id）。
- **只签到不随礼**：确认时 amount = 0。

### 5.6 统一约定

- **响应结构**：`{ ok: true, data }` / `{ ok: false, error: { code, message } }`。
- **错误码**：`UNAUTHORIZED` / `FORBIDDEN` / `NOT_FOUND` / `VALIDATION` / `CONFLICT` / `RATE_LIMITED` / `INTERNAL`。
- **分页**：`?page=&pageSize=`，返回 `{ items, total, page, pageSize }`。
- **时间**：数据库存 UTC 毫秒，对外用 ISO 字符串，展示按 `Asia/Shanghai`。
- **金额**：接口以整数（分）传输，前端负责元 / 分转换。
- **并发 / 幂等**：审核确认用条件更新（仅 `status = pending` 可确认），避免重复确认。
- **公网地址**：`PUBLIC_BASE_URL` 用于拼接专属链接 / 二维码 / 海报。
- **归档保留**：宾客归档只设置 archived_at，回执、签到、礼金和guest_id全部保留；恢复使用原编号，统计按独立状态计算。

### 6.2 三端页面

**管理后台 `/admin/*`（Ant Design）**
- 仪表盘：关键指标卡 + 图表
- 宾客管理：表格 + 增删改 + 导入导出 + 生成链接/二维码/海报
- 回执管理：列表 + 统计 + 修改
- **现场审核**：待审列表（轮询 3–5s）+ 补录礼金 + 确认/驳回
- 签到列表、礼金流水、导出
- 按角色隐藏无权限菜单（staff 只见：现场审核、签到列表、礼金流水单笔、宾客只读搜索）

**请柬页 `/invite/:token`（Tailwind + framer-motion）**
- 全屏封面 → 问候 → 新人 → 倒计时 → 时间地点（一键导航）→ 流程 → 相册故事 → 回执表单 → 联系与分享
- 中式国风红金/水墨视觉，图片懒加载、骨架屏

**自助签到页 `/checkin`（Tailwind）**
- 单页：输入姓名 → 提交 → 明确反馈

### 6.3 前后端协作

- 开发时 Vite dev server 通过 proxy 转发 `/api` 到本地 Node。
- 生产构建后，SPA 产物由 Node 托管，`/api` 与静态资源同源，免跨域。
- 接口类型从 `shared/` 共享（路径别名 `@shared` 引用），减少手写重复类型。

## 7. 安全设计

| 项 | 方案 |
| --- | --- |
| 密码 | bcrypt 哈希，永不明文存储 |
| 会话 | JWT 放 httpOnly + SameSite=Lax + Secure Cookie |
| 角色 | 中间件按 `admin` / `staff` 校验，服务端强制（不依赖前端隐藏） |
| 专属链接 | 随机 token（≥ 22 位），不可枚举 |
| 公开接口 | 按 IP 限流；自助签到可加简单去重 |
| 登录保护 | 失败次数限制 / 简单退避 |
| 传输 | 全程 HTTPS（Caddy 自动证书） |
| 数据 | 仅新人服务器持有，无第三方外发 |

**工作人员权限（服务端强制）**：可做现场审核、签到、礼金录入与单笔查看、宾客只读搜索；**不可**访问统计 / 看板 / 导出 / 总额。

## 8. 部署方案

### 8.1 容器

- `app`：Node 服务（多阶段构建：先构建前端，再打包后端运行）
- `caddy`：反向代理 + 自动 HTTPS
- volume：`./data`（SQLite）。图片素材为仓库内置静态资源（demo 占位），**无上传功能**

### 8.2 docker-compose（示意）

```yaml
services:
  app:
    build: .
    environment:
      - NODE_ENV=production
      - DB_PATH=/data/wedding.db
      - JWT_SECRET=${JWT_SECRET}
      - ADMIN_USERNAME=${ADMIN_USERNAME}
      - ADMIN_PASSWORD=${ADMIN_PASSWORD}
      - STAFF_USERNAME=${STAFF_USERNAME}
      - STAFF_PASSWORD=${STAFF_PASSWORD}
      - PUBLIC_BASE_URL=${PUBLIC_BASE_URL}   # 例 https://wedding.example.com，用于拼链接/二维码/海报
      - TZ=Asia/Shanghai
    volumes:
      - ./data:/data
    restart: unless-stopped

  caddy:
    image: caddy:2
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data
    depends_on: [app]
    restart: unless-stopped

volumes:
  caddy_data:
```

### 8.3 首次初始化

1. 准备服务器 + 域名解析
2. `docker compose up -d --build`
3. 启动时若 `users` 表为空，用环境变量里的账号密码**自动写入两个账号**（admin / staff）
4. 访问域名登录后台

### 8.4 备份

- SQLite 文件即全部数据，定期复制 `./data/wedding.db` 即可
- 后台提供 Excel / JSON 导出作为补充
- 可选：容器内每日 `sqlite3 .backup` 到带日期的文件

### 8.5 上线环境准备（腾讯云 · 中国香港）

**选型结论**：使用腾讯云**中国香港地域**的轻量应用服务器（Lighthouse）+ 域名 + Caddy。香港节点**免备案**、内地访问延迟低，对请柬 / 签到这类轻页面完全够用。

内地访问参考延迟：华南 10–40ms、华东 30–60ms、华北 40–80ms；晚高峰可能升高，轻页面可接受。

#### 8.5.1 准备清单

| 项目 | 说明 | 参考成本 |
| --- | --- | --- |
| 腾讯云账号 | 注册并完成**个人实名认证** | 免费 |
| 域名 | 腾讯云轻量域名 `.com` 约 10 元起/首年，或其它注册商 | ¥10–70/年 |
| 轻量应用服务器 | **中国香港**地域，建议 2核2G / 30Mbps / 50GB SSD / 1TB 月流量 | ¥30–60/月 |
| SSL 证书 | **不需要单独购买**，Caddy 自动签发 | 免费 |
| 快照备份 | 开启腾讯云**免费快照** | 免费 |

合计约 **¥100–200**（用 1–2 个月）。

#### 8.5.2 详细步骤

**Step 1 · 注册并实名腾讯云账号**
1. 打开 `cloud.tencent.com` 注册账号
2. 完成**个人实名认证**（身份证 + 人脸核验）
3. 绑定微信 / 手机号，方便登录

**Step 2 · 购买域名**
1. 控制台 → **域名注册**（或轻量控制台 → 域名），也可在其它平台购买
2. 选一个 `.com` / `.cn` 域名，完成**域名实名认证**
3. 若域名在腾讯云，后续解析用 **DNSPod** 直接配置

**Step 3 · 购买香港轻量应用服务器**
1. 购买页：`buy.cloud.tencent.com/lighthouse`
2. **地域：中国香港**（务必选香港；选成内地就需要备案）
3. 套餐：**2核 2G / 30Mbps / 50GB SSD / 1TB 月流量**（1核1G 也能跑）
4. 镜像：**Debian 12** 或 **Ubuntu 22.04 LTS**；也可直接选**「Docker CE」应用镜像**，省去装 Docker
5. 购买时长：**按月**（1 个月起即可）
6. 下单支付（支持支付宝 / 微信），记下实例的**公网 IP**

**Step 4 · 初始化服务器**
1. 轻量控制台 →「重置密码」设置 root 密码，或绑定 **SSH 密钥**
2. 可直接用轻量控制台的**网页终端（OrcaTerm）**登录，无需本地 SSH 工具
3. 建议开启**免费快照**（控制台 → 快照）

**Step 5 · 配置防火墙**
1. 轻量控制台 → 该实例 → **防火墙**，放行：
   - `22`（SSH，建议只允许你的 IP）
   - `80`（HTTP，供 Caddy 申请证书）
   - `443`（HTTPS）
2. 其余端口保持关闭

**Step 6 · 域名解析**
1. 在 DNSPod（或域名所在平台）添加两条解析：
   - `A` 记录，主机记录 `@` → 服务器公网 IP
   - `A` 记录，主机记录 `www` → 服务器公网 IP
2. 等待生效（一般几分钟），本地 `ping 你的域名` 应返回该 IP

**Step 7 · 安装 Docker（若已选 Docker 应用镜像可跳过）**

```bash
curl -fsSL https://get.docker.com | sh
docker version && docker compose version
```

**Step 8 · 部署应用**
1. 把代码放到服务器：`git clone` 或 `scp` 上传
2. 创建 `.env`，填入域名、`JWT_SECRET`、管理员 / 工作人员账号密码
3. 修改 `Caddyfile` 里的域名为你的域名
4. 启动并观察证书签发：

```bash
docker compose up -d --build
docker compose logs -f caddy
```

**Step 9 · 验证**
1. 浏览器访问 `https://你的域名`，地址栏应显示**锁标**（证书有效）
2. 用**不同运营商**的手机 4G/5G 各访问一次，确认速度
3. 微信内把链接发给自己，确认能正常打开
4. 走一遍主流程：请柬打开 → 回执提交 → 扫码自助签到 → 后台审核确认

**Step 10 · 备份与彩排**
1. 每日备份 `./data/wedding.db` 到异地，或依赖快照
2. 婚礼前 1–2 天做一次**全程彩排**（多台不同运营商手机实测）

#### 8.5.3 内地访问与封禁风险

| 担心 | 结论 |
| --- | --- |
| 没备案会不会被封 | **不会**，香港服务器不涉及备案 |
| 会不会被墙 | **不会**，婚礼内容不敏感 |
| 微信里能不能打开 | **能**，正常 HTTPS 外链 |
| 真正的风险 | 服务器被入侵滥用 / 内容违规 / 劣质共享 IP |

**规避要点**
- 强密码或密钥登录、只开 22/80/443、及时更新系统
- 选大厂（腾讯云）的独立干净 IP
- 定期导出数据；**域名不变，换机器只需改解析**，被墙也能半小时切换

#### 8.5.4 备案常见疑问（备查）

- 备案的正式对象是**网站**，记录绑定「**主体 + 域名 + 接入商**」三要素，故口语称"域名备案"。
- 域名已备案时：
  - 自己备的、接入商即当前云 → 一般可直接用（必要时做变更 / 新增网站）。
  - 自己备的、接入商是别的云（如阿里云备的、现用腾讯云）→ 需做**新增接入**，否则被拦截。
  - 域名是**别人**备的 → 不能用，需过户或自行重备。
  - **服务器在香港 / 海外 → 无论域名是否备案，都不需要备案**。

**HTTPS 说明**：Caddy 自动申请与续期 Let's Encrypt 证书，前提是域名解析生效且 80/443 可达。

**微信使用注意**：普通 HTTPS 链接即可在微信内打开、扫码跳转与唤起导航，**不需要**微信 JS-SDK，因此不涉及公众号 / JS-SDK 域名校验与备案。海报二维码同理，扫码即打开。
