# 宾客端完整流程联调

2026-10-22。延续「玄朱 · 浮光」宾客端与「深侧栏 · 珊瑚」后台，验证已还原页面之间的真实业务衔接。

## 环境和边界

- 真实 React 生产构建，实际 invite/checkin/checkins/guests/stats/auth 路由和数据库迁移。
- 独立临时 SQLite 数据库；使用虚构宾客与临时账号。本机 `journey.localhost` 子域隔离 Cookie，不覆盖日常后台登录会话。
- 故障只由临时联调服务在真实接口前后注入，不修改正式路由或业务规则。正式数据库没有测试写入。
- 没有上传照片、发布网站或发送邀请；没有在本轮通过手机摄像头扫描二维码。

## 实际页面验收

| 流程 | 结果 |
| --- | --- |
| 专属请柬 → 保存回执 | 陈星满填写 3 人、其中儿童 1 人，保存成功；后台预计人数为 3 |
| 提交签到 → 响应丢失 → 刷新重试 | 服务端已落库，模拟返回网络错误；页面保留姓名，刷新重试只指向原提交，待审没有重复增加 |
| 同名身份核对 | 两位陈星满分别属于新郎同事、新娘同学；提交不自动选中某位，同名选择明确显示 ID、分组、归属、回执与签到状态 |
| 回执带入 → 现场修改 | 选定新郎同事后带入 3 人、儿童 1 人；现场改为实到 2 人、儿童 1 人，没有改写原预计人数 |
| 审核保存失败 → 重试 | 姓名选择、人数和备注保留；重试成功后抽屉关闭、队列移除、名单显示已签到和实到人数 |
| 仅签到 | 不生成礼金记录，反馈明确“未登记礼金” |
| 后台确认 → 宾客再次查询原提交 | 保留原请求标识，刷新再提交返回“已完成签到”；不是按姓名推断成功 |
| 修改专属回执 | 保存为“暂未确定”后刷新可恢复；隐藏人数填写，既有实际签到人数没有被回执修改覆盖 |
| 通用回执与同名专属回执 | 同名通用回执独立保存，刷新恢复姓名及人数；不会接管专属回执或自动关联名单 |
| 下一位宾客 | 清空上一位姓名与提交标识；林知夏独立进入待审，核对身份后完成仅签到 |
| 未保存保护 | 手工补录输入后取消会提示；继续填写保留输入，明确丢弃后关闭；再次打开是空白新草稿 |

临时数据库只读核验：4 份宾客档案、2 条已确认签到、2 个提交标识、0 条礼金；两条同名回执分别为专属与未关联 ID 的通用记录。两条签到分别关联实际选定的宾客 ID。

## 本轮修复

发现审核抽屉在关闭动画结束前清空当前记录，导致短暂显示空标题、“提交 #undefined”及空姓名摘要。

修复局限于审核功能 Hook 与视图：关闭状态和当前填写对象分离；保存或取消后先关闭，Ant Design 原生 `afterOpenChange(false)` 再释放记录。关闭期间禁止再次保存，不显示“待审记录已被他人处理”的误导警告；重新打开或切换对象仍重置对应草稿、保留原未保存保护。共享 AdminDrawer 不增加业务状态。

真实页面再次确认林知夏时，关闭动画内标题仍为“核对签到 · 林知夏”，提交编号仍为 #2；不再出现 undefined。动画结束后内容销毁，重新打开手工补录无旧姓名。

## 回归检查

新增 `tests/guest-journey.test.ts`，用真实路由和临时数据库覆盖两条跨接口流程：

1. 专属/通用同名回执 → 自助重复提交 → 工作人员同名核对 → 仅签到 → 工作台/统计 → 回执修改和实际人数独立。
2. 散客自助登记 → 未确认人数保留未知 → 工作人员审核 → 重试读取已确认结果，同时覆盖未登录和工作人员统计权限。

Node24 下 `pnpm check` 通过：全项目零错误，保留原有 92 条服务端/测试警告；前端零警告，6 项分层规则、132 项业务测试、TS7 类型检查及构建通过。修改文件已格式化，`git diff --check` 通过。

- 当前宾客提交结果页不会自动轮询后台确认状态。本轮“已完成签到”验证使用刷新后重试同一次提交；没有新增公开查询接口或宣称实时推送。
- 微信内置浏览器的键盘、地址栏伸缩、安全区、后退与 Cookie 保留仍需真机验收；桌面尺寸模拟不能代替真实手机。
