# 婚礼管理应用 · 需求文档（PRD）

> 版本：v0.7（待评审）
> 状态：草案，用于需求对齐
> 更新日期：2026-10-10
> 说明：本文档只描述"要什么"，不涉及任何技术设计与实现方案。

---

## 1. 项目背景与目标

### 1.1 背景
新人要举办一场婚礼，需要一个**自用**的轻量应用，覆盖婚礼前后与当天的核心流程：

- 婚前：向宾客发送电子请柬、收集出席回执
- 当天：宾客现场扫码自助签到（只填姓名），工作人员在后台补录礼金并审核确认
- 全程：在一个后台里看清所有数据（谁来了、收了多少礼金）

### 1.2 目标
- **够用就好**：只服务婚礼这一个场景，不追求通用性与商业化。
- **省心**：新人（两位程序员）能低成本地长期维护和使用。
- **好看**：请柬是宾客对婚礼的"第一印象"，视觉必须精美（中式国风 · 红金 / 水墨）。
- **当天要稳**：现场签到与记礼金要顺手、要防错、要能实时看到结果。

### 1.3 非目标（明确不做）
- 不做多场婚礼同时管理（只服务"我们这一场"）。
- 不做多租户 / SaaS，不做在线支付与银行对账。
- 不做宾客端注册登录，不做复杂权限体系。
- 不做原生 App（宾客与工作人员用手机 / PC 浏览器即可）。
- **不做桌位分配**。
- **不做祝福墙**。
- **不做背景音乐**。
- **不做新提交提醒**（现场靠工作人员主动查看待审列表）。

### 1.4 已确定的约束
- 使用场景为本场婚礼，**非商业、非多租户**。
- 宾客规模约 **150 人**。
- 婚礼信息（新人姓名、婚礼时间、地点、文案、图片、婚礼流程等）**直接写在代码中，后台不提供配置界面**。
- 图片、文案等素材**先用 demo 占位**，后续由新人补齐。
- 后台设**两个账号**：管理员（新人）账号与工作人员账号；**仅一位工作人员，不区分经手人 / 审核人**。
- 所有数据**永久保留**，不做定期清理。
- 部署在**新人自有的服务器**上，数据由新人自己掌握。

## 2. 用户角色与使用场景

| 角色 | 使用设备 | 账号 | 说明 | 主要诉求 |
| --- | --- | --- | --- | --- |
| **新人（管理员）** | PC 浏览器 | 管理员账号 | 拥有全部权限 | 管宾客、发请柬、看回执、看统计、导出 |
| **宾客** | 手机浏览器 | 无需账号 | 收到请柬链接；当天扫码自助签到 | 看请柬、填回执、导航到场地、自助签到（只填姓名） |
| **现场工作人员** | PC 浏览器 | 工作人员账号（**仅一位**） | 仅现场相关功能，权限受限 | 核对宾客提交、补录礼金、审核确认 |

**典型场景**

1. 婚礼前，新人在后台录入宾客名单，为每位宾客生成专属请柬并发送（微信手动发送）。
2. 宾客在手机上打开精美请柬，看到新人信息、时间地点、流程，并填写是否出席、几人等回执。
3. 新人随时在后台查看回执统计，安排酒店桌数。
4. 婚礼当天，现场展示**一个入口总码**；宾客扫码，只填姓名后提交。
5. 提交实时推送到 PC 后台，现场工作人员登录工作人员账号，逐条核对、补录礼金（金额必填，可为 0）并**审核确认**。
6. 新人登录管理员账号，实时看到签到人数、礼金总额，并在事后导出全部数据。

## 3. 产品构成

产品由**三个使用界面**组成，三者共享同一份婚礼数据：

1. **管理后台**（PC）：给两位新人与现场工作人员使用，是数据的总入口、总览与审核台；**按账号区分权限**。
2. **请柬页**（手机）：给宾客使用，是婚礼的"门面"，要求精美。
3. **自助签到页**（手机）：给宾客当天扫码使用，自助提交姓名。

三个界面各有独立入口且相互隔离：宾客只能看到请柬与自助签到页；管理后台需要登录。

## 4. 功能需求 · 管理后台（PC）

> 婚礼信息（新人姓名、时间、地点、文案、图片、婚礼流程等）写在代码中，后台不提供配置界面。

> **一级菜单**：仪表盘 / 宾客管理 / 回执管理 / 现场审核 / 签到记录 / 礼金管理 / 导出。
> 工作人员账号仅可见：现场审核、签到记录、礼金管理（单笔）、宾客只读搜索。

### 4.1 宾客管理
> 管理员可增删改查；工作人员仅可**只读搜索**宾客名单，用于现场核对姓名。

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| 宾客增删改查 | 录入与维护每位宾客信息 | P0 |
| 批量导入 | 用 Excel / CSV 批量导入，提供标准模板；**部分行失败时给出失败明细，成功行照常导入** | P1 |
| 批量导出 | 导出为 Excel / CSV | P1 |
| 搜索 / 筛选 / 排序 | 按姓名、手机号、分组、归属方、回执状态筛选 | P0 |
| 分组管理 | 亲戚 / 朋友 / 同事 / 同学 / 邻里…（可自定义） | P1 |
| 归属方 | 男方 / 女方 / 双方 | P1 |
| 专属邀请链接 | 为每位宾客生成唯一、不可被他人猜测的邀请链接 | P0 |
| 二维码 | 为宾客链接生成二维码，便于打印或发送 | P1 |
| 专属海报 | 为每位宾客生成一张请柬海报，版式相同、**仅二维码不同**；扫码即打开其专属请柬 | P1 |
| 批量海报导出 | 批量生成并打包下载全部宾客海报 | P1 |
| 邀请发送记录 | **手动标记**是否已发送、记录发送时间 | P1 |
| 批量操作 | 批量生成链接、批量复制、批量修改分组 | P1 |
| 宾客详情 | 查看单个宾客的回执、签到、礼金汇总 | P1 |

**宾客需要维护的信息**

- 姓名（必填）
- 称谓（用于请柬称呼，如"张先生"）
- 手机号
- 关系分组
- 归属方（男方 / 女方 / 双方）
- 是否已发送邀请、发送时间
- 当前状态（见 7.1 状态说明）
- 备注

> **散客自动建档**：现场未匹配到名单的姓名，会自动在宾客表中新建一条记录，与手动录入的宾客同等对待。

**宾客专属海报**

- 每位宾客一张海报，**背景与版式完全相同，只有二维码不同**。
- 海报中的二维码即该宾客的专属请柬链接，扫码 / 长按识别后直接打开他的请柬页。
- 生成后可单张查看 / 下载，也可**批量生成打包下载**。
- 图片尺寸适合手机查看与微信转发；如需要，可另排出可打印的版本。
- 由新人自行在微信中手动发送给对应宾客。

### 4.2 回执管理（RSVP）
> 仅管理员账号可用。

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| 回执列表 | 展示出席状态、出席人数、随行儿童、祝福留言 | P0 |
| 回执统计 | 确认出席人数、不出席人数、待定人数、出席率 | P0 |
| 回执详情 | 查看单个宾客的完整回执与留言 | P0 |
| 手动补录 / 修改 | 新人代宾客补填或修改回执 | P1 |

**回执需要记录的信息**

- 是否出席（出席 / 不出席 / 待定）
- 出席人数（含本人）
- 随行儿童人数
- 祝福留言
- 提交时间

## 5. 功能需求 · 请柬页（手机，宾客用）

> 这是产品的"门面"，视觉必须精美。基调：**中式国风 · 红金 / 水墨**。

### 5.1 视觉与体验
| 项 | 要求 | 优先级 |
| --- | --- | --- |
| 整体风格 | 中式国风、红金配色 / 水墨元素，喜庆而不土气 | P0 |
| 首屏 | 全屏封面（新人姓名 + 囍字 / 纹样 + 婚礼日期），有"打开请柬"引导 | P0 |
| 动效 | 卷轴展开、印章落下、花瓣飘落等入场动画，克制、流畅 | P1 |
| 字体 | 标题使用书法 / 衬线风格，正文清晰易读 | P1 |
| 适配 | 移动端优先，主流机型尺寸自适应；电脑打开时居中呈现 | P0 |
| 打开速度 | 首屏要快，图片需要适当压缩、按需加载，避免长时间白屏 | P0 |

### 5.2 内容板块（自上而下）
1. **封面**：全屏视觉 + 新人姓名 + 婚礼日期 + "打开请柬"引导。
2. **个人化问候**：如"亲爱的张先生…"；**无称谓时回退为"亲爱的 + 姓名"**。
3. **新人介绍**：新人照片 + 一句邀请语。
4. **倒计时**：距婚礼还有 X 天 X 时 X 分。
5. **婚礼信息**：日期、时间、场地名称、详细地址，并提供**一键导航**（唤起系统地图）。
6. **婚礼流程**：时间轴。
7. **相册 / 故事**：照片轮播 + 新人故事文案。
8. **回执表单**：见 5.3。
9. **联系与分享**：一键拨打新人电话、分享请柬。

> 封面图、相册、故事、文案等素材开发期**先用 demo 占位**，后续由新人补齐。

### 5.3 回执表单
| 字段 | 填写方式 | 是否必填 |
| --- | --- | --- |
| 是否出席 | 出席 / 不出席 / 待定 三选一 | 是 |
| 出席人数 | 数字（含本人） | 出席时必填 |
| 随行儿童 | 数字 | 否 |
| 祝福留言 | 多行文本 | 否 |

**行为要求**
- 宾客打开请柬即视为"已查看"（后台状态随之更新）。
- 回执允许**重复提交并覆盖**（宾客可能改主意），后台始终保留最新结果。
- 再次打开时**预填上次提交的内容**，方便修改。
- 提交成功要有中式风格的反馈动效（如印章 / 拱手），并明确提示"**已收到，可再次修改**"。

### 5.4 分享与传播
- **专属链接**：每位宾客收到唯一、不可被他人猜测的专属请柬链接。
- **专属海报**：每位宾客一张海报，除二维码外内容一致，扫码即打开其请柬页。
- **通用链接**：另提供一条通用请柬链接，便于宾客之间互相转发。
  - 通过通用链接打开时可查看请柬；填写回执时**由宾客自行输入姓名**。
- 支持使用手机系统分享、或一键复制链接。
- 不生成分享文案，由新人自行在微信中手动发送。

### 5.5 异常处理
- **无效 / 失效的请柬链接**：给出友好提示（如"请柬链接有误，请联系新人"），不暴露内部信息。
- **签到页被转发**：任何打开者都可提交，姓名由填写者自负（无人脸 / 身份验证）。
- **重复提交**：回执与签到均允许重复提交，但给出提示。

## 6. 功能需求 · 自助签到页（手机，宾客扫码）

> 婚礼当天现场使用。宾客扫码后**只填写姓名**并提交，随后由工作人员在 PC 后台补录礼金并审核确认。

### 6.1 进入方式
- 现场展示**一个入口总码**（可放入口、投屏或打印），不做访问限制。
- 宾客扫码即可进入自助页面，**无需登录**。

### 6.2 自助流程
1. 输入姓名
2. 提交，数据推送到 PC 后台的待审核列表

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| 扫码进入 | 扫现场入口总码即可进入，无需登录 | P0 |
| 输入姓名 | 宾客只填写自己的姓名 | P0 |
| 匹配名单 | 姓名与后台宾客名单匹配则关联；**未匹配的自动在宾客表新建为散客** | P0 |
| 提交 | 提交后进入待审核状态 | P0 |
| 提交反馈 | 显示"已提交，请等待工作人员确认" | P1 |
| 重复提交提示 | 同一姓名重复提交时给出提示（但仍允许重名） | P1 |

### 6.3 现场体验要求
- **大按钮、大字号**，适合匆忙与单手操作。
- **弱网容错**：网络不佳时给出清晰提示与重试，避免重复提交。
- **明确反馈**：提交成功 / 失败有清晰提示，让宾客知道"是否需要再操作"。

## 7. 业务规则汇总

1. **宾客状态流转**：待邀请 → 已发送 → 已查看 → 已回执。
2. **回执可覆盖**：同一宾客多次提交以最后一次为准。
3. **请柬访问即计入"已查看"**。
4. **现场提交状态**：待审核 → 已确认 / 已驳回。
5. **只有"已确认"的提交才计入签到人数与礼金统计**；待审核与已驳回均不计入。
6. **礼金由工作人员填写，且必填**；没有随礼则填 **0**。
7. **重名允许**：宾客姓名不要求唯一；提交时按姓名匹配名单，命中多条时由工作人员在审核时选择，**未命中则自动在宾客表新建为散客**。
8. **礼金方式固定为三种**：微信 / 支付宝 / 现金。
9. **礼金可多笔**：一位宾客可有多笔记录。
10. **签到与礼金相互独立**：宾客可只签到不随礼（礼金记 0），也可只随礼未签到。
11. **临时宾客**：现场未匹配的散客**自动进入宾客表**，同样可供后台查看。
12. **删除与撤销**：误操作可驳回 / 删除，**驳回即直接删除**，删除后统计随之更新。
13. **礼金可见性**：工作人员账号可查看**单笔**礼金明细，但**看不到总额、汇总与统计**；总额与统计仅管理员可见。
14. **仅一位工作人员**：不区分经手人 / 审核人。
15. **数据永久保留**：不做定期清理。
16. **金额范围**：礼金金额 ≥ 0，并设上限防止误输。
17. **并发审核**：同一条提交被同时确认时，后到的操作应被拒绝并提示。
18. **批量导入**：部分行失败时给出失败明细，成功行照常导入。
